Static lint for unattended agent routines

Rot Check

Paste an agent prompt, a SKILL.md, a cron line or a Windows scheduled-task definition. It highlights wording related to 14 ways an unattended agent dies quietly — the ones that leave no error, no crash and no gap you would notice. It reports signals, not a verdict: it cannot tell a live defect from a quoted example, and it never checks whether anything actually ran. Everything runs in your browser. Nothing is uploaded.

First — get your routine out

Windows Task Scheduler

List what you actually have:

Get-ScheduledTask | Where-Object {$_.TaskPath -notlike "\Microsoft*"} | Select-Object TaskName,TaskPath

Then export one as XML and paste it above:

schtasks /query /TN "\YourTaskName" /XML

Copy the output straight from the console. Add > task.xml to save it instead — the file is UTF-16, which is normal.

cron — Linux, macOS, WSL

Your own crontab:

crontab -l

The system ones people forget:

cat /etc/crontab ls -la /etc/cron.d/

Paste one line or the whole file. A single cron line can only answer 2 of the 14 checks — the checker says so rather than inflating the score.

systemd timers

Find the timer:

systemctl list-timers --all

Then dump the unit it drives:

systemctl cat NAME.timer NAME.service

Paste both units together — Persistent=true is the catch-up setting this checks for.

launchd — macOS

List your agents:

launchctl list | grep -v com.apple

Then read the plist:

cat ~/Library/LaunchAgents/LABEL.plist

Substitute the label from the third column. System-wide jobs live in /Library/LaunchDaemons/.

Agent prompts and scripts

No command needed — open the file and copy it.

A SKILL.md, a scheduled agent prompt, or the shell/PowerShell script your scheduler calls. These carry the most evidence, so they answer the most checks. If you have both the schedule and the script it runs, check them separately — they fail in different ways.

What this is, exactly

Signals, not verdicts

This reports which phrasings it found, not whether your routine works. Reliability is a runtime property — whether the token was valid, whether the host woke, whether the file was really written. None of that is visible in text. A guard signal is a phrase match. It is not a pass.

Absence is not evidence

A short input cannot prove a dead-man alarm is missing. So checks that could apply but found nothing report UNKNOWN, and checks the input type structurally cannot carry are marked NOT VISIBLE and excluded from the trace.

Mention vs use is unsolved

The tool matches wording across the whole document. It cannot distinguish a live instruction from a quoted counterexample or a rule forbidding it. So a well-written routine that names the failure it guards against will light a defect signal. That is a known limit, not a finding about your config. The 14 named failure modes are the point; the regexes are only how they get surfaced.

The 14 failure modes are drawn from a seven-routine fleet that stopped for three days without a single routine noticing, and from a zero-byte flag file that was accepted as proof of a completed business send for six days. Neither was a crash. Both were routines that looked fine because the only thing checking them was themselves. Rot Check v1 · no network calls, no telemetry, no accounts.
